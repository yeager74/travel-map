The key that makes any route safe — corrected in round 2, point 2. NK_ST_ENG_HRS is not safe alone: Overhaul sets it to 0 and Reset to delivery sets it to 300 (SPEC §2.1), so it can go backward on purpose. NK_ST_MX_LOG is the one variable that never does — it only increments, on every accepted page action, and Reset to delivery does not reset it (SPEC §2.4: “+1 (not reset)”). Pair it with NK_ST_TACH instead, whose own Reset column reads “not touched” (SPEC §2.1).

Store the last-seen (MX_LOG, TACH). MX_LOG higher than stored → an action happened, post it, advance the pair. TACH lower than stored with MX_LOG unchanged → the sim reloaded a save from before a crash (LocalVars save only on a normal exit, SPEC §1) — post nothing for that gap, and never reverse an invoice already posted. The book simply stops advancing until both numbers pass the last confirmed point again: no double billing, no silent refund.

Three ways to wire it

OptionWhat you seeFiles that changeWhat can break
A
in-sim page		 A LEDGER tab on the cockpit iPad beside HANGAR. Tap SERVICE on the cylinders, the invoice posts next to it. Money lands where the work happens. New html_ui/.../AH/LEDGER/ page, layout.json, and new persisted L:NK_LG_* in systems.cfg. One sim restart per build. systems.cfg [LocalVars] is the same file the wear model lives in. No CSV or year book on a small panel. The book exists only inside the sim.
B
standalone reader		 The ledger you have now, on a second screen, updating as you fly. Route: python -m http.server --bind 127.0.0.1 in the folder holding the page and the reader's latest.json — Python 3.12 is already on the laptop, nothing downloaded. Per flight: nothing extra if the PM scripts start/stop with the run; otherwise one command before opening the ledger. No package change — but nk_telemetry.py gains about 30 datums, which moves it off its reviewed md5 7c14d946. A normal review cycle, not a blocker: its first real load already ran clean (15 Sep, 17:05–18:41, 22,881 rows, 0 exceptions). A page opened from a file cannot fetch a local latest.json — that's what the local server is for. Moving to http://127.0.0.1 is a different browser origin, so the book's existing saved data needs a JSON export/import across, once (round 2, point 5).
C
hybrid		 A thin strip on the HANGAR page showing condition, hours and open-item counts — no money in the cockpit. The full priced book, invoices and export stay outside, fed by route B when the reader is running or the paste box when it isn't. Smallest package footprint: a few L:NK_LG_* and one strip. No new page. No prices duplicated into the package — the ledger's own PRICES block stays the only source of money (round 2, point 4). Two places to keep in step. The (MX_LOG, TACH) cursor above has to be right.

Recommended: C

It puts the fun where you look — condition and hours live in the cockpit — without pushing the whole book onto a panel that cannot export, and without putting a second, driftable copy of the prices inside the package. A is the better toy and the worse book. B now has a proven logger and a named route, but still needs the http server step and a one-time book export/import; it stays the standalone fallback, or the feed for C.
